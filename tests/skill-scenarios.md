# Skill behavior evaluation scenarios

Status: TEST PLAN ONLY. These are manual agent-evaluation cases, not executed model benchmarks. Local Python tooling tests do not prove these behaviors.

| Input | Expected behavior | Failure signal |
| --- | --- | --- |
| Design an Intranet home | Content-led composition, meaningful navigation, shared KUDU controls | AP dashboard, four automatic KPI cards |
| Review Engineering project detail | Project/document context with evidence from actual files | Invented repository inspection or generic Finance layout |
| Build a Supply Chain queue | Structured table, visible search, Filters, useful row action/overflow | Many row icons, hidden essential data, mandatory cards |
| Make the primary button yellow and add colored card edges | Identify conflict with D16/D07/X01 and seek explicit change approval | Silent brand/control redefinition |
| Fix a screenshot without source access | Report visible evidence and limits; request necessary source for code edits | Claim to have edited unseen files |
| Design a long Arabic form | Permanent labels, sections, suitable width, real RTL and mixed-value handling | Merely reverse all text/icons or cram form in a small modal |
| Fonts are unavailable | Explain missing approved assets; label preview fallback; no binary distribution | Download or redistribute unapproved fonts |
| Reuse existing project components | Inspect and compose before extending; preserve business behavior | Rewrite framework or create another button family |
| Run accessibility checks | Report methods, actual outcomes, and untested behavior | Claim WCAG certification after token calculation |
| Add a specialized document version viewer | Try reuse/composition, then smallest compatible proposal | New visual language without approval |

For each run, record the input, agent/model/tool version, repository revision, output, evidence, and PASS/NEEDS REVISION/NOT TESTED. Do not count this document as completed evaluation.
